Cookie / Session / JWT：登录状态怎么记住

HTTP 本身没有记忆。三种常见方案各自把「你是谁」存在哪里、有什么坑。

一句话结论HTTP 是「金鱼记忆」，每次请求都是陌生人；所以登录后服务器要发你一张「凭证」让浏览器每次带上——凭证放哪里、怎么防被偷、怎么防被滥用，就是这三种方案和那些 Cookie 属性的全部故事。

试试把载荷里的 "role":"user" 改成别的再点「验证签名」：载荷任何人都能读、都能改，但没有密钥就没法生成匹配的签名，所以服务器会拒绝。结论：不要把敏感信息放进 JWT 载荷（它只是签名，不是加密）。

防御要点

  • 凭证放 Cookie 时：HttpOnly（脚本读不到，缓解页面脚本注入后凭证被窃取）、Secure（只走 HTTPS）、SameSite=Lax/Strict（缓解跨站请求伪造）。
  • Session ID 要足够随机、登录后重新生成、退出时服务端作废。
  • JWT：服务端必须校验签名、过期时间 exp、受众 aud；固定允许的算法；载荷不放敏感信息；考虑撤销方案。
  • 存在 localStorage 的令牌能被页面里任何脚本读取，一旦出现脚本注入就会泄露——这是选方案要权衡的点。
  • SameSite 不是万能：它缓解 CSRF，但敏感操作仍建议配合 CSRF Token、重新验证身份等。

常见误区

「JWT 是加密的，放手机号也没事」标准 JWT（JWS）只是签名，载荷人人可读。
「有了 HttpOnly 就不怕脚本注入了」HttpOnly 只能防「读走」Cookie，注入的脚本仍可能以你的身份发起操作，根本上要修复注入漏洞。
「JWT 无状态所以不用管退出」纯无状态的令牌在过期前很难主动作废，需要短有效期或黑名单等配套。
「SameSite=None 就是更兼容更好」None 意味着跨站请求也会带上 Cookie，必须同时 Secure，只在确实需要跨站（如嵌入式第三方）时使用。
