浏览器同源策略与 CORS

为什么你的请求「明明发出去了」却被浏览器拦住？预检请求又是什么？

一句话结论同源策略是浏览器给「网页脚本」上的锁：默认不让 A 站的脚本读 B 站的响应；CORS 是 B 站用响应头「主动开门」的办法——拦的是「读响应」，不是「发请求」，而且是浏览器在拦，不是服务器。

先弄懂「同源」

同源 = 协议、域名、端口三者完全相同。

    什么是预检（preflight）？

    当跨域请求不是「简单请求」时，浏览器会先偷偷发一个 OPTIONS 请求问服务器：「我马上要用 PUT 方法、带 X-Token 头，你允许吗？」服务器同意了，才发真正的请求。

    「简单请求」条件（CORS-safelisted）：方法是 GET / HEAD / POST，且只含安全的头，且 Content-Type 只能是 text/plain、application/x-www-form-urlencoded、multipart/form-data 之一。所以发 JSON（application/json）一定触发预检。

    防御视角：怎么配才对

    • 只对确实需要的来源放行：服务端用白名单校验 Origin 再回写，而不是无脑回写请求里的 Origin。
    • 带凭证时 Allow-Origin 不能是 *，必须是具体来源，并配合 Allow-Credentials: true。
    • CORS 不是身份认证；接口本身仍需要鉴权，且不要依赖 CORS 阻止 CSRF（简单请求照样会发到服务器）。
    • 放行方法和头越少越好。

    常见误区

    「CORS 是服务器拦住了我」服务器通常已经处理了请求；是浏览器看到响应头不对，才不把结果交给脚本。用 curl 或服务器端代码请求根本不受 CORS 约束。
    「设了 CORS 头就能防别人调我的接口」CORS 只约束浏览器里的网页脚本，不是访问控制。
    「Allow-Origin: * 最省事」公开的、不含用户隐私的资源可以；带登录态的接口别这样。
    「localhost:3000 和 localhost:8080 是同源」端口不同就是不同源。
