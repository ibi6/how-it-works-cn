数据库索引为什么快

用可视化的 B+ 树，亲眼看「翻遍全表」和「顺着索引找」差多少步。

一句话结论索引就是一本「排好序的目录」：不用一页页翻整本书（全表扫描），而是顺着目录的几层指引直接跳到目标页——B+ 树让层数只有 3~4 层，哪怕有上亿行。

🌲 B+ 树索引

从根到叶，每个节点相当于读一个磁盘页

本树每个节点最多 3 个键（阶数很小，便于观察分裂）。真实数据库一个节点是 8~16KB 的页，能放几百个键。图中叶子之间的 → 表示叶子链表，范围查询（BETWEEN）就靠它顺着扫。

怎么「读懂」这棵树

  • 内部节点只存「路标」（分隔键），不存数据；叶子节点存真正的键（和行位置/行数据），并串成有序链表——这是 B+ 树区别于 B 树的关键。
  • 插入：找到该去的叶子；放不下了就分裂成两个，把中间键「提」到父节点；父节点满了继续分裂，必要时树长高一层。所以树永远是平衡的，所有叶子同一深度。
  • 代价：索引占空间；每次写入要多维护一棵树。读多写少的列才值得建。

什么时候索引会「失效」

  • 对列做函数/运算：WHERE YEAR(created)=2026，通常用不上 created 的索引。
  • 联合索引不满足最左前缀。
  • 区分度很低的列（如性别）：走索引再回表，未必比全表扫描快。
  • 用 EXPLAIN 看真实执行计划，不要猜。

常见误区

「索引越多越好」每个索引都拖慢写入、占磁盘。
「建了索引就一定走索引」由优化器按成本估算决定。
「二叉树就够了，为啥用 B+ 树」二叉树太高（一亿行约 27 层），每层一次磁盘读；B+ 树「矮胖」，层数 3~4。
