参数化查询为什么能防 SQL 注入

不讲攻击套路，只讲一个原理：让「代码」和「数据」永远分开。全部在浏览器里用假数据库模拟。

一句话结论SQL 注入的根源是把用户输入拼进了 SQL 文本，于是数据有机会被数据库当成「代码」解析；参数化查询先把 SQL 的结构定死，再把输入当作纯「数据」单独传入，数据再怎么奇怪也不会变成代码。
本课范围：只使用页面内置的假数据库和一个约 60 行的迷你查询器，不连接任何真实系统，不提供攻击清单；目的是让你看懂「为什么安全」并写出正确的代码。

看懂这个对比

  1. 拼接：数据库收到的是一整段文本，它自己切词、解析。输入里的引号会提前结束字符串，后面的内容被当成 SQL 语法——「数据」变成了「代码」。连 O'Brien 这样完全合法的名字都会直接报语法错误，这本身就是「拼接不可靠」的信号。
  2. 参数化：SQL 模板先被解析（? 只是占位符），生成固定的结构；参数随后被「绑定」到占位符的位置，作为一个值整体使用，不会再被解析为 SQL。引号、关键字、注释符都只是普通字符。
简化示意：真实数据库的驱动实现不一定把预编译与执行分成两步发送（有的在客户端按类型规则安全转义/绑定），但对使用者而言「结构与数据分离」的保证是一致的。

正确写法速查

// Node.js（mysql2 / pg 的占位符风格不同，示意）
const [rows] = await db.execute('SELECT id,name FROM users WHERE name = ? AND pass_hash = ?', [name, hash]);

# Python（sqlite3 / DB-API）
cur.execute("SELECT id, name FROM users WHERE name = ?", (name,))

// Java（JDBC）
PreparedStatement ps = conn.prepareStatement("SELECT id,name FROM users WHERE name = ?");
ps.setString(1, name);

// PHP（PDO）
$st = $pdo->prepare('SELECT id,name FROM users WHERE name = :n'); $st->execute([':n' => $name]);

参数化不能解决的，要这样处理

  • 表名、列名、ORDER BY 方向不能用参数绑定：用固定白名单映射（如前端传 sort=price，后端查表映射成固定的列名）。
  • ORM 的原生 SQL 接口（raw、literal）同样不能拼接，要用它提供的绑定参数。
  • 最小权限：应用账号只给需要的表、需要的操作权限，出问题时损失最小。
  • 输入校验是辅助（类型、长度、格式），不是替代。
  • 不要把数据库错误原样返回给用户，记录到日志即可。

常见误区

「过滤掉单引号 / 关键字就行了」黑名单永远有遗漏，也会误伤 O'Brien 这类正常数据。根治方法是结构与数据分离。
「用了 ORM 就绝对安全」ORM 的参数化接口安全，但一旦把用户输入拼进 raw SQL 就回到原点。
「前端校验过了」请求可以绕过前端直接到达后端，校验必须在服务端。
「存储过程天然安全」存储过程内部如果再拼接动态 SQL，同样有问题。
