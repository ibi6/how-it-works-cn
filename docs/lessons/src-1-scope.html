第 SRC 1 课

什么是 SRC？合法边界在哪里

先学会「不越界」，再谈挖洞：授权范围、禁止行为、平台规则要点。

一句话结论SRC（Security Response Center，安全应急响应中心）是企业公开邀请白帽子「在规定范围、按规定方式」帮忙找漏洞的渠道。有授权才测，范围之外不碰，点到为止，立刻报告——这是底线，比任何技术都重要。
本页是通用科普，不是法律意见。各国/地区法律（如我国《刑法》《网络安全法》《数据安全法》等）对未经授权的访问、数据获取有明确规定，请自行查阅最新条文，并以各平台、各项目的最新规则为准。

SRC / 漏洞赏金 / 众测是什么关系

🏢 企业 SRC

企业自己运营的收洞渠道，如各大厂的 SRC，规则、范围、奖励都写在官网公告里。

🌐 漏洞平台

第三方平台聚合多家企业项目，统一审核、结算，如国内的补天，国外的 HackerOne 等。

👥 众测

企业在限定时间内邀请一批白帽测试某个具体系统，范围更窄、规则更细。

🧪 动手试试：这样做合法吗？

下面是一个虚构的项目规则。读完后，对每个行为选「可以」或「不可以」，看看你的边界感。

【虚构项目：示例商城 SRC】
范围内：  *.shop.example.com 下的官方网站、官方 App
范围外：  pay.shop.example.com（第三方支付页）、所有第三方服务、员工个人账号
禁止：    拒绝服务/压力测试、社会工程学、物理攻击、读取/下载他人数据、
          批量扫描、测试时影响真实用户
要求：    仅使用自己注册的测试账号；发现漏洞立即停止并报告；报告前不公开

授权范围（scope）怎么读

  • 范围内资产：只测明确列出的域名/IP/App。不在列表里 = 没授权，哪怕看起来是同一家公司的。
  • 漏洞类型：有的项目明确「不收」某些类型（如纯理论的、需要用户重度交互的、无安全影响的），测之前先看。
  • 测试方式：是否允许自动化工具、频率上限、测试账号要求。
  • 数据底线：证明漏洞存在只需要最小证据（如自己的账号能看到「别人的订单」的自己造的第二个测试账号的订单），不要去翻、存、传真实用户数据。

红线清单（通用）

❌ 绝对不要

  • 没授权就测试（「我只是看看」也不行）
  • 拿到漏洞后继续深入、横向移动、留后门
  • 下载、保存、展示真实用户数据
  • 用漏洞换钱、敲诈、威胁企业「不给赏金就公开」
  • 造成服务中断（DoS、大量写入脏数据）
  • 利用漏洞做和证明无关的事

✅ 应该做

  • 先读规则，确认范围与允许的方式
  • 只用自己的测试账号和测试数据
  • 验证到「能证明存在」就停
  • 尽快、私下、完整地报告
  • 漏洞修复前不公开细节
  • 不确定？先问项目方，或不测

常见误区

「网站没有 SRC，我测了发现问题告诉他们是在帮忙」没有授权就是未授权访问，善意不等于合法。没有公开渠道的站点，请不要测。
「只是扫一下，没做什么破坏」未经授权的扫描本身可能就违规；而且扫描会给对方带来负载与告警。
「同一家公司，子域名肯定也算范围」以规则里写的范围为准，通配符才包含子域。
「漏洞被忽略/评低，我就公开它」未经允许公开未修复漏洞，可能违反规则甚至法律。有分歧走申诉/平台仲裁。
