常见 Web 漏洞：为什么出现、怎么修

不教攻击，只讲成因、影响与修复，并用本地假数据演示两个最典型的「缺了一道检查」。

一句话结论绝大多数 Web 漏洞的根子只有两类：把不可信的输入当成了可信的（注入类），以及少做了一道权限/校验检查（访问控制类）。理解成因，修复思路就是顺理成章的。
本课所有演示都在你的浏览器里、用页面自带的假数据，不涉及任何真实系统，也不提供针对真实站点的攻击载荷清单。

🧪 动手试试①：XSS 的本质——输出时没有「转义」

想象一个留言板。下面输入框的内容会被「显示」出来。输入一段带 HTML 标记的文字，比如 <b>你好</b>，对比两种显示方式（都放在禁用脚本的沙箱里，安全）。

❌ 当作 HTML 直接拼进页面输入里的标记被浏览器当成「代码」解析了：数据变成了代码。如果换成能执行脚本的标记，就是 XSS。
✅ 输出时转义（当作纯文本）< 变成 &lt;，浏览器只把它当文字显示。

🧪 动手试试②：越权（IDOR）——只差一道检查

虚构场景：订单接口 GET /api/orders/{id}。你是用户 小明，只该看到自己的订单。切换服务端是否「检查订单属于当前用户」，再点其他订单号。

点击订单号
只靠「ID 不容易猜」不是防护——ID 是可以被枚举、泄露的。根本做法是每次访问都做授权检查。

常见类型速览

共通的防御思路

  • 永远不信任输入：服务端校验类型/长度/范围；输出时按场景转义；数据库用参数化。
  • 默认拒绝：每个接口显式做认证 + 授权，而不是「忘了加就开放」。
  • 纵深防御：CSP、HttpOnly、SameSite、最小权限、日志告警叠加，单点失守不致命。
  • 安全默认值：框架自带的转义、CSRF 保护别随手关掉。

常见误区

「前端把按钮隐藏了就没人能点」权限必须在服务端判断，前端隐藏只是体验。
「用了 HTTPS 就不会有这些漏洞」HTTPS 只保护传输，不管应用逻辑。
「漏洞等级高就是技术难度高」最危险的往往是最朴素的：少一行权限检查。
