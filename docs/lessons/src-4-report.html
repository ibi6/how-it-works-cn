漏洞报告怎么写，怎么沟通

同一个漏洞，好报告几小时被复现，差报告石沉大海。

一句话结论好报告 = 让对方不用问你任何问题就能复现、评估和修复：标题说清「哪里、什么问题」，影响讲清「能造成什么后果」，步骤能照做，并附修复建议。

🧪 动手试试②：这个漏洞大概几级？

各平台有自己的定级标准（常参考 CVSS），最终以平台审核为准。这里用三个问题帮你建立直觉：

好报告的清单

  • ✅ 标题：哪个资产 + 什么类型 + 一句话后果，别写「发现一个漏洞」。
  • ✅ 影响：用业务语言讲清后果和影响范围，不夸大。
  • ✅ 步骤：编号、可复制、写明测试账号和前置条件，附截图/请求响应（打码敏感信息）。
  • ✅ 证据最小化：只证明漏洞存在，不附任何真实用户数据。
  • ✅ 修复建议：给方向（不必写完整补丁），体现你理解成因。
  • ✅ 一个报告一个漏洞；同源多点的合并说明，不要刷数量。

沟通礼仪

✅ 这样沟通

  • 礼貌、客观，对事不对人
  • 对方要补充信息，及时、具体地回复
  • 被判重复/忽略：先看规则，再理性申诉，附补充证据
  • 修复前保密，修复后经允许再写文章
  • 耐心：审核、修复都需要时间

❌ 不要这样

  • 催促、施压、威胁「不给钱就公开」
  • 夸大危害博高等级
  • 一个洞拆成十份刷数量
  • 报告里附他人真实数据
  • 私下把细节发给第三方

常见误区

「报告越长越好」要的是复现信息完整，不是篇幅。
「只写“存在XSS”，他们自己会验证」不给出位置和步骤，大概率被要求补充甚至关闭。
「评了低危是看不起我」定级看影响与利用条件；用事实说话，认真学习对方给出的理由。
