XSS 跨站脚本（反射 / 存储 / DOM）

数据被当成代码执行在别人的浏览器里

定义类比成因危害防御审计视角本地实验靶场小测验误区报告模板
一句话定义XSS 是指：网站把「不可信的内容」未经处理就输出到页面里，浏览器把它当成了网页代码执行，于是攻击者的脚本以受害者的身份在该网站里运行。
本课只讲原理、防御与审计思路。所有演示都是浏览器里的假数据模拟；不提供针对真实目标的攻击载荷清单，也请只在自己搭建的环境或获得授权的范围内验证。

🏠 生活类比

小区公告栏允许住户贴纸条。如果物业不检查，有人贴一张「纸条」，上面写着「看到本条的人请把家门钥匙放到门口」，并盖上物业的章——大家以为是物业发的，就照做了。XSS 里，「盖物业章」就是脚本借用了网站的身份。

🔍 成因：问题到底出在哪

根因只有一个：输出时没有按"输出位置"做转义。浏览器分不清哪些是网站作者写的结构，哪些是用户提供的文字。按数据"来自哪、落在哪"，分成三种：

反射型

输入来自当前请求（如 URL 参数），服务端立刻把它拼进响应。只影响点击了特制链接的人。

// 伪代码：搜索页
render("<h2>搜索结果：" + request.query["q"] + "</h2>")

存储型

输入被保存进数据库（评论、昵称、工单），之后每个查看该页面的人都会中招，危害最大。

// 伪代码：评论列表
for c in db.comments:
    render("<li>" + c.content + "</li>")   // 直接拼接

DOM 型

整个过程发生在前端：前端 JS 读取 URL / 存储里的数据，用 innerHTML 等"当作 HTML"的接口写入页面，服务器甚至看不到。

// 前端 JS
const name = new URLSearchParams(location.search).get("name");
document.getElementById("hi").innerHTML = "你好，" + name;

💥 危害与等级

高存储型且出现在高访问页面（后台、客服工单）：可在管理员浏览器里以其身份操作，等于账号权限被借用。
中反射型 / DOM 型：需要诱导点击；可伪造页面内容、钓鱼、读取页面上的数据。
低仅影响自己（Self-XSS）、或页面无敏感数据且有严格 CSP：通常 SRC 不收或低危。
决定等级的因素① 页面是否带登录态 ② 谁会看到（普通用户/管理员）③ 是否有 HttpOnly、CSP 等缓解 ④ 页面上有什么数据。

🛡 防御与修复

修复原则：输入校验是辅助，输出转义是主力，CSP 是兜底。

// 1) 服务端模板：使用自动转义的模板引擎（默认开启，不要关）
//    {{ comment.content }}        → 自动转义
//    {{ comment.content | safe }}  → 危险：只给可信内容用

// 2) 前端：需要"当文字"写入时，用 textContent，而不是 innerHTML
document.getElementById("hi").textContent = "你好，" + name;

// 3) 确需富文本：用成熟的净化库白名单过滤（如 DOMPurify），不要自己写正则
el.innerHTML = DOMPurify.sanitize(userHtml);

// 4) 响应头兜底
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'
Set-Cookie: sid=...; HttpOnly; Secure; SameSite=Lax

🧐 怎么判断自己安全？代码审计视角

  • 全局搜索危险接口：innerHTML、outerHTML、document.write、v-html、dangerouslySetInnerHTML、模板里的 |safe / raw。
  • 每处用户可控数据，追问：它最终落在 HTML 正文、属性、JS 字符串还是 URL？是否用了对应场景的转义？
  • 富文本功能是否使用白名单净化？链接是否限制了 javascript: 协议？
  • 检查 CSP 是否真的有效（不要 unsafe-inline 一把梭），Cookie 是否 HttpOnly。

✅ 小测验

⚠ 常见误区

「过滤掉 script 标签就行」脚本能通过事件属性、伪协议等许多途径执行，黑名单永远列不完。
「HttpOnly 能防 XSS」它只防止脚本读 Cookie，脚本依然能以你的身份发请求。
「只有搜索框才有 XSS」昵称、头像 URL、文件名、HTTP 头里的内容、错误提示都可能被输出。

📝 SRC 报告里怎么描述（虚构示例模板）

下面是完全虚构的示例（example.test 不是真实站点）。注意三点：标题含等级与位置、复现步骤最小化且只用自己的账号、说明影响但不扩大验证。写法细则见 漏洞报告与沟通。

标题：【中危】example.test 个人资料页昵称存储型 XSS（虚构示例） 目标/接口：https://app.example.test/profile （虚构目标，已在授权范围内） 漏洞概述：个人资料页的"昵称"字段保存后在好友列表页被原样输出到 HTML，未做转义。 复现步骤： 1. 使用测试账号 A 登录，进入"设置—昵称"。 2. 在昵称中输入一段无害的标记文本，例如加粗标签，保存。 3. 使用测试账号 B 打开好友列表，发现 A 的昵称被渲染为加粗，说明输入被当作 HTML 解析（概念验证仅用无害标记，未执行任何脚本，未接触他人数据）。 影响：好友列表是高访问页面；若将标记替换为可执行脚本，可在任意查看者的会话中执行操作。 修复建议：服务端模板对昵称做 HTML 转义；启用 CSP；Cookie 增加 HttpOnly。 自评等级：中危（需用户查看页面触发，页面含登录态）。
