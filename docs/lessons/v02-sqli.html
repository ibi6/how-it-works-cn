SQL 注入

输入被拼进 SQL，数据变成了指令

定义类比成因危害防御审计视角本地实验靶场小测验误区报告模板
一句话定义SQL 注入是指：程序把用户输入直接拼接进 SQL 语句文本，导致输入里的内容被数据库当作"指令"的一部分执行。
本课只讲原理、防御与审计思路。所有演示都是浏览器里的假数据模拟；不提供针对真实目标的攻击载荷清单，也请只在自己搭建的环境或获得授权的范围内验证。

🏠 生活类比

你在点餐单上写"一份炒饭"。如果服务员不加思考地把整张单子大声念给后厨，而你写的是"一份炒饭；另外把今天的收入全给我"，后厨就可能真的照做。问题不在厨师，在于"点单内容"与"指令"没有分开。

🔍 成因：问题到底出在哪

数据库收到的是一串文本，它自己要解析这串文本。拼接让"用户的数据"与"开发者的结构"混在同一串文本里，解析器无法区分。

登录场景

输入影响了条件逻辑。

// 有漏洞：字符串拼接
sql = "SELECT * FROM users WHERE name='" + name + "' AND pwd='" + pwd + "'"
// 当 name 里出现单引号，就能提前结束字符串，改写后面的条件

数字/排序场景

没有引号也一样，数字位置同样可被拼接。

sql = "SELECT * FROM goods WHERE id=" + request.id + " ORDER BY " + request.sort
// 注意：ORDER BY 的列名、表名无法参数化，必须用白名单

二次注入

输入第一次被安全地存下，但之后被程序取出再拼接进另一条 SQL。

// 注册时安全入库（用了参数化）
// 但后台导出功能：
sql = "SELECT * FROM log WHERE user='" + stored_name + "'"   // 取出后又拼接

💥 危害与等级

严重能读取全库（用户表、密码哈希、订单）、篡改或删除数据；某些数据库配置下还可能进一步控制服务器。
高只能读取部分表，或认证绕过（不输密码登录任意账号）。
中仅能造成报错、信息泄露（库名、版本）。
决定等级的因素① 数据库账号权限 ② 能读到什么数据 ③ 是否需要登录 ④ 是否影响他人数据。

🛡 防御与修复

修复原则：代码与数据分离——参数化查询（预编译）。

// 正确：占位符，输入永远只是"值"
cursor.execute("SELECT * FROM users WHERE name=%s AND pwd_hash=%s", (name, hash))

// ORM 也要小心原生拼接
User.objects.filter(name=name)                 // 安全
User.objects.raw("... WHERE name='%s'" % name)  // 又拼接了！

// 无法参数化的位置（表名/列名/排序方向）：白名单
ALLOWED = {"price", "created_at"}
if sort not in ALLOWED: sort = "created_at"

// 纵深：数据库账号最小权限（应用账号不能 DROP、不能读无关表）；错误信息不回显

🧐 怎么判断自己安全？代码审计视角

  • 搜索所有执行 SQL 的地方：看有没有字符串 +、format、f"..."、% 拼接。
  • ORM 的 raw / execute / extra / Sequelize.query 是重点。
  • ORDER BY、表名、列名、LIMIT 是否做了白名单或强转数字？
  • 应用数据库账号是否是 root / DBA？错误页是否把 SQL 报错原样返回？

✅ 小测验

⚠ 常见误区

「用了 ORM 就不会有注入」ORM 的原生 SQL 接口、排序字段、动态过滤同样会拼接。
「过滤 select、union 等关键字」黑名单易被绕过，且常误伤正常内容。
「内部系统不用管」内网一旦失守，注入就是最短的数据窃取路径。

下面是完全虚构的示例（example.test 不是真实站点）。注意三点：标题含等级与位置、复现步骤最小化且只用自己的账号、说明影响但不扩大验证。写法细则见 漏洞报告与沟通。

标题：【高危】example.test 订单查询接口 id 参数 SQL 注入（虚构示例） 目标/接口：GET https://shop.example.test/api/orders?id=（虚构） 漏洞概述：id 参数在服务端被拼接进 SQL；传入不匹配的引号时接口返回数据库语法错误。 复现步骤： 1. 登录测试账号，访问 /api/orders?id=1，返回自己的订单。 2. 将 id 改为 1 后接一个单引号，接口返回 500 及数据库语法错误信息。 3. 改为 1 后接恒等式条件，返回条数与原先不同，证明条件被拼入 SQL。到此为止：未读取任何其他用户的数据，未尝试提取库内容。 影响：可进一步读取订单与用户表（需遵守规则，未验证）。 修复建议：改用参数化查询；应用数据库账号降权；生产环境关闭 SQL 报错回显。 自评等级：高危（无需特殊权限；影响面为全库，未实际读取）。
