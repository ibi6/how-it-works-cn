不安全的反序列化

把别人寄来的"压缩包"直接还原成了程序里的对象

定义类比成因危害防御审计视角本地实验靶场小测验误区报告模板
一句话定义序列化是把对象变成可存储/传输的字节或文本；反序列化是把它还原。不安全的反序列化是指：对不可信的数据执行还原，而还原过程会触发代码（构造器、魔术方法），数据被当成了"指令"。
本课只讲原理、防御与审计思路。所有演示都是浏览器里的假数据模拟；不提供针对真实目标的攻击载荷清单，也请只在自己搭建的环境或获得授权的范围内验证。

🏠 生活类比

你收到一个"组装家具"的快递：包裹里只是零件还好；如果里面是带说明书的"自动机器人，开箱即运行"，你一拆封它就动了。

🔍 成因：问题到底出在哪

某些语言的原生序列化格式（Java 序列化、Python pickle、PHP unserialize、.NET BinaryFormatter 等）在还原时可以实例化任意类并调用其方法。程序里已有的类组合起来（称"gadget 链"）就可能产生危险行为。

把序列化对象放进 Cookie/参数

客户端可控 → 可篡改。

// 有漏洞：Python
user = pickle.loads(base64.b64decode(request.cookies["user"]))

篡改数据本身

即使没有代码执行，反序列化出来的字段（如 role）也被信任。

user = deserialize(cookie)
if user.role == "admin": ...   // 数据来自客户端，没有签名

概念示例

序列化数据里指定了类名，反序列化器照做。

{"__class__": "TempCleaner", "path": "/tmp/x"}   // 数据决定了"创建什么对象"

💥 危害与等级

严重远程代码执行（gadget 链可用时）。
高权限提升：篡改序列化数据里的身份字段。
中拒绝服务（超大/深度嵌套的对象）。
决定等级的因素序列化格式是否能触发代码、依赖库里是否有可用 gadget、数据来源是否可被用户控制。

🛡 防御与修复

修复原则：不要对不可信数据使用原生反序列化；用纯数据格式 + 校验 + 签名。

// 1) 使用 JSON 等"只有数据、没有类型"的格式
user = json.loads(body)

// 2) 严格的结构校验（schema），只接受预期字段与类型
validate(user, schema={"name": str, "role": ["user"]})

// 3) 需要放在客户端的数据 → 服务端签名（HMAC）并验证
if not hmac_ok(data, sig): abort(400)
// 更好：只在客户端放不透明的会话 ID，数据存服务端

// 4) 如果必须使用原生反序列化：类白名单（如 Java ObjectInputFilter）、隔离、低权限
// 5) 升级依赖，移除不必要的高风险库

🧐 怎么判断自己安全？代码审计视角

  • 搜索：pickle.loads、unserialize、ObjectInputStream、BinaryFormatter、yaml.load（非 safe_load）。
  • 反序列化的数据来自哪里？Cookie、参数、消息队列、缓存、上传文件？
  • 是否有完整性校验（签名）？是否有类型白名单？

✅ 小测验

⚠ 常见误区

「Base64 后就看不懂了」编码不是加密，更不是签名。
「内部系统间传输没事」消息队列/缓存被污染时同样危险。
「加黑名单就好」gadget 层出不穷，黑名单追不上。
