漏洞详解 12/15

业务逻辑漏洞（支付 / 验证码 / 竞争条件）

每一行代码都"正确"，合起来的规则却有洞

定义类比成因危害防御审计视角本地实验靶场小测验误区报告模板
一句话定义业务逻辑漏洞是指：程序没有"技术上的错误"，但流程设计里缺少约束，使用户可以以设计者没想到的方式使用功能，从而获利或越权。
本课只讲原理、防御与审计思路。所有演示都是浏览器里的假数据模拟；不提供针对真实目标的攻击载荷清单，也请只在自己搭建的环境或获得授权的范围内验证。

🏠 生活类比

超市规定"退货原价退款"。收银系统没限制"同一商品只能退一次、必须有对应的购买记录"，有人拿一张小票反复退。每个步骤都按规则运行，规则本身漏了。

🔍 成因：问题到底出在哪

这类漏洞没有统一的"特征字符串"，扫描器几乎找不到，靠的是理解业务。常见三大类：

支付与金额

价格、数量、优惠券由客户端提交并被信任；数量为负数；价格精度；重复使用优惠券；回调未验签。

// 有漏洞：金额由客户端提交
amount = request.json["price"] * request.json["qty"]
// qty 为负 → 金额为负 → "退款"变成"充值"

验证码与流程

验证码太短、可无限次尝试、不失效、响应里直接返回；跳过前置步骤；找回密码令牌可预测。

// 有漏洞：验证码 4 位数字，且无次数限制
if request.code == session.code: allow()
// 一万次以内必猜中

竞争条件

"检查"和"执行"之间有空隙，并发请求同时通过检查（先检查余额再扣款）。

// 有漏洞
if balance >= amount:      // ① 检查
    # …… 此处另一请求也通过了检查
    balance -= amount      // ② 扣款

💥 危害与等级

严重直接资金损失：0 元购、无限提现、优惠券刷取。
高账号接管（验证码/找回流程）、绕过审批。
中薅羊毛、刷单刷量，影响营销活动。
决定等级的因素能获得的价值、是否可规模化/自动化、是否需要特定条件。

🛡 防御与修复

修复原则：服务端是唯一可信方：价格、状态、次数全部由服务端决定与校验。

// 1) 金额只在服务端算，客户端只传商品 ID 与数量；校验数量范围
item = db.get_item(id); qty = int(qty); assert 1 <= qty <= 10
amount = item.price * qty

// 2) 验证码：6 位以上、短时效、一次性、限制尝试次数（如 5 次锁定）、不回显

// 3) 竞争条件：把"检查+修改"变成原子操作
UPDATE accounts SET balance = balance - 100 WHERE id = ? AND balance >= 100;
-- 检查影响行数；或使用事务 + 行锁 / 唯一约束 / 幂等键

// 4) 状态机：每一步校验前置状态；支付回调验证签名与金额
// 5) 风控与审计日志：异常行为告警

🧐 怎么判断自己安全？代码审计视角

  • 每个涉及钱/积分/次数/状态的接口：哪些参数来自客户端？服务端是否重新计算和校验？
  • 有没有"先查再改"的代码？是否在事务中，是否加锁或使用原子 SQL？
  • 验证码/令牌：长度、有效期、重试次数、是否复用？
  • 流程是否强制顺序（状态机）？

✅ 小测验

⚠ 常见误区

「前端限制数量就行」直接请求接口，前端限制无效。
「验证码 4 位够用了」没有次数限制+短时效，几千次内必猜中。
「并发是极端情况」高并发下很常见，自动化可以轻易制造。

📝 SRC 报告里怎么描述（虚构示例模板）

下面是完全虚构的示例（example.test 不是真实站点）。注意三点：标题含等级与位置、复现步骤最小化且只用自己的账号、说明影响但不扩大验证。写法细则见 漏洞报告与沟通。

标题：【高危】example.test 提现接口竞争条件导致余额超取（虚构示例） 目标/接口：POST https://pay.example.test/api/withdraw（虚构） 漏洞概述：提现接口先查询余额再扣减，非原子；并发请求可重复通过检查。 复现步骤： 1. 在测试账号、最小金额（如 1 元）上同时发起两个提现请求。 2. 两个请求均返回成功，账户被扣减的金额小于两次提现之和。 3. 验证后立即联系厂商，未进行大额或重复操作。 影响：可超额取款，造成资金损失。 修复建议：原子 SQL 或事务加锁；幂等键；风控告警。 自评等级：高危（直接资金损失）。
