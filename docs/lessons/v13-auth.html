弱口令与认证缺陷

大门装了锁，但钥匙是 123456，而且可以试无数次

定义类比成因危害防御审计视角本地实验靶场小测验误区报告模板
一句话定义认证缺陷指：网站在"确认你是谁"的环节有薄弱点——允许弱口令、无限尝试登录、重置流程可被滥用、会话管理不当，使账号容易被他人接管。
本课只讲原理、防御与审计思路。所有演示都是浏览器里的假数据模拟；不提供针对真实目标的攻击载荷清单，也请只在自己搭建的环境或获得授权的范围内验证。

🏠 生活类比

家门有锁（需要密码），但密码设成"1234"，而且你可以一直试，没有人拦；忘记钥匙时找物业"重置"，物业只问你"姓什么"。

🔍 成因：问题到底出在哪

认证是一条链：设置密码 → 登录 → 找回密码 → 会话维持 → 登出，任何一环弱，整体就弱。

弱口令与无限制登录

允许常见弱密码；对登录失败没有限速、没有锁定、没有告警。

// 有漏洞
if check_password(user, pwd): login()   // 无次数限制、无延迟

找回密码缺陷

令牌可预测、不过期、可重复使用；重置链接用 Host 头拼接；"验证码"随响应返回。

token = md5(user.id + time())   // 可预测

会话与凭证管理

登录前后会话 ID 不变（会话固定）；登出不使服务端会话失效；密码明文/弱哈希存储；Cookie 无 Secure/HttpOnly。

// 有漏洞：存储
user.password = md5(pwd)   // 快速哈希，泄露后易还原

💥 危害与等级

严重管理员账号弱口令、默认口令：直接接管后台。
高普通账号可批量被撞库/爆破；重置流程缺陷导致任意账号接管。
中缺少 MFA、会话策略弱，增加风险但需配合其他条件。
决定等级的因素被接管账号的权限、是否可规模化、是否有风控。

🛡 防御与修复

修复原则：强口令策略 + 限速风控 + 多因素 + 安全的重置 + 正确的会话管理。

// 1) 口令：长度优先（≥ 8~12），拒绝常见弱口令/已泄露口令，不强制奇怪的复杂规则
// 2) 存储：慢哈希（bcrypt / scrypt / Argon2）+ 每用户随机盐
pwd_hash = argon2.hash(pwd)

// 3) 登录：按账号 + IP 限速、渐进延迟、异常告警、必要时验证码；统一的错误信息，不区分"账号不存在/密码错"

// 4) 重置：高熵随机令牌、一次性、15–30 分钟过期、服务端存哈希；成功后使所有会话失效

// 5) 会话：登录后更换会话 ID；登出服务端销毁；Cookie 设 Secure / HttpOnly / SameSite
// 6) 提供 MFA（TOTP/Passkey）；管理后台强制 MFA 并限制来源 IP

🧐 怎么判断自己安全？代码审计视角

  • 注册/改密接口是否有口令策略？是否检查常见弱口令？
  • 登录是否限速？错误信息是否统一？
  • 找回密码令牌：生成方式、长度、有效期、是否一次性、是否与用户绑定？
  • 密码如何存储？会话登录后是否更换 ID？登出后是否真正失效？默认口令是否在部署文档中出现过？

✅ 小测验

⚠ 常见误区

「强制特殊字符就等于强口令」P@ssw0rd 复杂但常见；长口令短语更好。
「加验证码就够了」验证码可能被绕过或打码平台破解，仍需限速与风控。
「内部后台不用 MFA」后台是最有价值的目标。

📝 SRC 报告里怎么描述（虚构示例模板）

下面是完全虚构的示例（example.test 不是真实站点）。注意三点：标题含等级与位置、复现步骤最小化且只用自己的账号、说明影响但不扩大验证。写法细则见 漏洞报告与沟通。

标题：【高危】example.test 管理后台登录无速率限制且接受弱口令（虚构示例） 目标/接口：POST https://admin.example.test/login（虚构） 漏洞概述：后台登录接口无次数限制、无验证码，错误信息区分账号不存在与密码错误。 复现步骤： 1. 用自己的测试账号，连续提交少量（如 10 次）错误密码，均返回统一的处理时间，未触发锁定或验证码。 2. 账号不存在与密码错误返回不同提示，可用于枚举。 3. 没有进行任何大规模尝试，仅以少量请求证明缺少限制。 影响：攻击者可自动化猜解后台账号口令，导致后台接管。 修复建议：限速与锁定、MFA、统一错误信息、弱口令拦截。 自评等级：高危（后台入口、无防护）；若没有弱口令实证，可降为中危。
